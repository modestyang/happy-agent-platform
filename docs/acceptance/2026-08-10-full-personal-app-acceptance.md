日期：2026-08-10

## 结论

当前版本已形成适合个人应用的完整核心闭环：管理员可以配置 OpenAI-compatible 模型服务及其模型、把模型和工具绑定到同一个 Agent，并在调试台观察流式运行；新用户可以注册、建立目标、记录身体与饮食、与同一 Agent 流式对话，并在明确确认后保存训练计划。

本轮页面主流程未发现阻断使用的缺陷。Agent schema 在开发期只保留一个自包含的 `V1__agent_baseline.sql`，不再累计 V2、V3 或后续开发迁移；Fitness schema 仍按既定规则保持追加式迁移。

## 本轮已修正的关键问题

1. Agent 数据迁移从开发期 V1–V12 历史链收敛为唯一正确 V1；干净库 Flyway 日志只验证和应用 1 个 Agent migration。
2. Provider、Model、Tool、Skill、Hook、Prompt 等恢复为独立资源，移除前端对聚合工作台接口的单点依赖。
3. Provider 和 Model 均支持页面手动维护，并建立明确归属和联动；停用代替物理删除。
4. 模型调用会接收已发布 Agent 的工具描述；`fitness.plan.save` 已进入工具目录和 Agent 绑定，不是只存在于后端代码。
5. 健身聊天与调试聊天均支持流式响应、Markdown 和默认收起的安全执行摘要。
6. 训练计划写入增加用户确认门槛，确认后由后端工具持久化；计划页缓存已修正，保存后无需整页刷新。
7. 三餐空状态生成入口、Markdown 裸文本、Trace 手工 UUID 等先前 P1–P3 遗留项已一并处理。

## 仍建议改进

### P1：计划正文与确认卡只保留一个事实源

模型在确认卡前生成的自然语言计划，偶尔可能与后端冻结确认卡的动作或组数表述不完全一致。个人应用最直接的处理是：确认卡出现后以卡片为唯一可保存内容，正文只说明原则，或由服务端从冻结方案生成正文，避免用户疑惑。

### P1：发布后强制刷新 Agent 版本状态

发布成功后应立即重新读取草稿和已发布版本，让 revision、发布版本和按钮状态同时更新，避免管理员误以为仍需再次发布。

### P2：减少测试退出时的调度线程噪声

完整 Maven 测试退出码为 0，但 Spring 集成测试销毁 Testcontainers 时，后台调度任务仍可能短暂访问已关闭数据库并打印连接错误。建议测试 Profile 禁用调度任务，让失败日志更可信；这不影响当前生产运行。

### P3：后台与健身端按路由拆包

生产构建主 JS 约 559 kB。当前个人应用可用，但后续可以把管理后台和健身端按路由懒加载，改善首次打开速度，不需要引入微前端或平台化架构。
