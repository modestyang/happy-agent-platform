# AI 流式与确认式训练计划设计

## 目标

让健身应用 AI 聊天和 Agent 调试台都能即时看到输出进度、Markdown 正确排版和默认折叠的执行摘要；当 Agent 生成当天或未来 7 天训练计划时，先展示结构化提案，只有用户明确确认后才通过写工具保存。同时关闭新用户三餐无生成入口、Markdown 裸标记和 Trace 必须手填 UUID 三项验收遗留。

## 方案

采用持久 Run + SSE。消息提交只创建 Run 并立即返回标识，后台执行将有序事件落到 agent schema，SSE 根据 `Last-Event-ID` 推送并支持断线续读。健身端与调试台共用事件模型和前端消费器，不引入 WebSocket。

事件至少覆盖运行状态、文本增量、公开进度、Tool 阶段、训练计划提案、确认状态、错误和完成。页面中的“思考与执行”只展示公开进度、读取了哪些用户数据和 Tool 状态，默认收起；原始模型推理不会进入用户消息、Trace 或 SSE。

## 对话与确认流程

1. 页面提交消息，服务端创建 `RUNNING` Run 并立即返回 `runId`。
2. 页面连接 Run SSE；收到文本增量后持续追加到同一 assistant 消息并增量渲染 Markdown。
3. Agent 需要生成训练计划时，产生结构化提案。提案范围为 `DAY` 或 `WEEK`，包含 1 或 7 个按日期排列的日计划、标题、预计时长和已有动作库中的动作 ID/名称。
4. 服务端持久化与 `runId`、`userId` 绑定的确认记录，Run 进入 `WAITING_APPROVAL`，SSE 发送提案和确认事件。
5. 页面显示“确认保存 / 取消”卡片；调试台也使用同一交互，便于真实验证。
6. 确认端点以审批 ID 幂等更新状态并恢复 Run，只能执行审批记录中已冻结的参数，不能接受页面或模型重传用户 ID/计划内容。
7. `fitness.plan.save` 通过 `ToolExecutionContext.userId` 调用 Fitness service。保存当天或 7 天计划时，只替换相同日期下未完成计划；任何已完成计划保留。整份提案在 fitness schema 单事务内写入，重复审批不会重复创建。
8. 拒绝后不写数据库，Run 输出取消说明并结束。

## 数据边界

- agent schema 保存 Run、事件、确认状态和冻结的 Tool 参数；fitness schema 保存训练计划。
- 两个 schema 不建立外键、不跨 schema 查询、不共享事务。
- 审批恢复先以 agent 事务抢占一次执行权，再调用具备幂等键的 Fitness 用例；执行结果回写 agent Run。
- 新 migration 只新增文件，不修改既有已应用迁移。

## Markdown 与页面体验

- 使用 `react-markdown` 与 `remark-gfm` 替代手写解析，默认不启用原始 HTML。
- 流式未结束时允许不完整 Markdown，组件必须稳定渲染；完成后自然形成标题、列表、引用、表格、链接、行内代码和代码块。
- 外部链接新窗口打开并带安全 `rel`。
- 健身端沿用温暖、轻量的移动端卡片语言；确认卡优先展示范围、日期和时长，再折叠每日动作。
- 调试台沿用现有桌面工作台视觉，执行摘要更紧凑，并保留 Run Trace 链接。

## P1-P3

- P1：三餐空状态提供“立即生成”；生成中原位显示，失败原位重试，成功复用现有轮询和推荐卡。
- P2：完整 Markdown 渲染与流式消息共用一个组件，删除裸星号来源。
- P3：Trace 默认显示最近 Run；用户 UUID 仅作为可选筛选，不再作为进入页面的前置条件。

## 验证

按 TDD 添加协议、事件续读、审批幂等、日/周保存、已完成历史保护、Markdown、SSE 消费器、三餐空状态和 Trace 默认列表测试。整批结束后运行相关 Maven 模块测试、前端 Vitest、TypeScript、ESLint/格式化定向检查，并通过两个真实页面完成一次流式回复和一次确认保存冒烟。
