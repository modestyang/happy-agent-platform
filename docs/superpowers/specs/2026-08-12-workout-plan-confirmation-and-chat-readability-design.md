# 训练计划确认卡与聊天可读性修复设计

## 背景

训练计划生成链路存在三个相邻问题：

1. `fitness.plan.save` 的冻结参数只包含动作 ID。通用 Runtime 把这份参数原样投影为审批 `proposal`，移动端在缺少动作名称时又把 ID 当作名称，因此确认卡直接展示 UUID。
2. `fitness.exercise.candidates.query` 允许省略目标部位表示无部位偏好，但 `focusAreas` 白名单不接受用户和 Agent 常用的“全身”，导致 Tool 抛出“未知目标部位 全身”。
3. AI 对话正文固定为 `12px`，进度、确认卡按钮和部分辅助信息只有 `8–10px`，明显低于移动端聊天应用的常见阅读字号。

## 目标

- 训练计划确认卡展示动作库中的可信中文名称，不展示动作 UUID。
- 当候选查询收到单独的“全身”时，将其解释为无部位偏好，同时继续执行经验、器械和冲击等级硬限制。
- 将 AI 对话正文提高到 `16px`，确认卡、处理进度和建议词提高到 `14px`，辅助说明提高到 `11px`。
- 保持冻结审批参数、保存幂等、用户身份和 Fitness/Agent schema 边界不变。

## 非目标

- 不新增或修改公开 API 端点、OpenAPI 数据结构或数据库 migration。
- 不让模型提供的自由文本名称成为动作显示或保存的可信来源。
- 不修改训练计划保存规则、候选 SQL 硬限制、页面标题或底部导航字号。
- 不进行聊天页面之外的全局字号重设计。

## 方案选择

采用“可信 Tool 结果丰富展示 proposal”的方案。

不采用纯前端把 UUID 替换为“动作 1”的方案，因为它无法满足展示真实动作名称的目标。不采用在 `fitness.plan.save` 参数中要求模型同时提交名称的方案，因为模型提交的名称可能与冻结动作 ID 不一致。

候选查询和动作详情 Tool 已返回真实的 `exerciseId + name`。Runtime 在同一次 Run 内持有确认事件之前的有序 Tool 结果，可以据此构造仅用于展示的名称映射，而实际审批和保存仍使用原始冻结参数。

## 确认卡数据流

### 可信名称收集

Runtime 只检查当前 Run 实际绑定、且出现在确认事件之前的以下只读 Tool 结果：

- `fitness_exercise_candidates_query`
- `fitness_exercise_details_query`

绑定身份按精确 Tool key 校验，再从绑定描述中取得 runtime name 与事件匹配。对这两个结果进行结构遍历，只接受同时具有合法 UUID `exerciseId` 和非空字符串 `name` 的对象，生成 `Map<UUID, String>`。未绑定的同名事件、其他 Tool、模型正文、保存 Tool 参数中的显示名称均不进入该映射。

同一个 ID 多次出现时使用最早取得的非空名称；这两个 Tool 都读取同一动作库，正常情况下名称一致。若结果结构无法解析，则忽略该条数据，不影响审批冻结和后续保存。

### 展示 proposal

Runtime 从 `fitness.plan.save` 的冻结参数读取 `scope`、`days` 和每一天的 `exerciseIds`，生成审批事件中的展示 proposal：

```json
{
  "scope": "DAY",
  "days": [
    {
      "scheduledFor": "2026-08-13",
      "title": "全身循环训练",
      "estimatedMinutes": 20,
      "exercises": [
        { "exerciseId": "...", "name": "深蹲" }
      ]
    }
  ]
}
```

展示 proposal 不写回 `agent_run_approvals.arguments`。用户确认后，Runtime 仍从审批记录读取冻结的 `exerciseIds`，注入 `approvalId`，再调用 `fitness.plan.save`。

如果某个 ID 在可信结果中找不到名称，proposal 使用按日从 1 开始的“动作 1”“动作 2”作为显示降级，绝不把 UUID 作为名称。该降级只影响显示；保存仍按冻结 ID 执行，并继续由 Fitness service 校验动作是否存在。

### 前端兼容

`AgentRunMessage` 优先消费 `days[].exercises[]`。对于旧 Run 或异常事件中只有 `exerciseIds` 的 proposal，前端同样使用“动作 1”“动作 2”降级，不再把 ID 复制到 `name`。

这保留历史 Run 的可渲染性，也防止任何遗漏再次暴露 UUID。确认、取消、提交中和终态行为继续复用现有 `ConfirmationCard`。

## “全身”目标部位语义

`focusAreas` 继续允许最多 3 个具体目标部位。归一化规则为：

- `null`、空数组：无部位偏好。
- `['全身']`：归一化为空数组，语义同无部位偏好。
- `['全身', '核心']` 等混用：拒绝，并返回“全身不能与具体部位同时使用”。
- 具体部位继续限制为现有闭合集合：臀腿、核心、胸部、背部、肩部、手臂、心肺。
- 空值、重复值、超过 3 个值和未知具体部位继续拒绝。

归一化后的空数组进入现有 SQL。SQL 仍按经验、器械和冲击等级过滤 eligible 动作，再按目标部位和动作模式均衡排序；“全身”不会成为新的数据库 `target_area`，也不会绕过任何硬限制。

Tool 参数描述补充上述闭合标签和“全身”的别名语义，降低 Agent 再次构造未知值的概率。

## 字号与布局

字号只作用于 `.ai-page` 内的聊天体验：

- `.message-body`：`16px/1.65`。
- `.run-progress`、确认卡标题/范围标签/日期/动作摘要/消息/按钮、建议词：`14px`；处理进度与确认卡正文行高为 `1.55`。
- 结构化卡片眉题、表格滑动提示和会话自动结束说明：`11px/1.45`。
- `.composer input`：保持 `16px`，避免 iOS 聚焦时页面缩放。
- 页面标题、AI 名称和底部导航：保持现状。

字号提升后继续保留现有 `min-width: 0`、安全断行和局部横向滚动规则。确认卡按钮仍为两列；窄屏内容允许文字自然换行，不通过压回小字号适配。

## 处理进度的时序与位置

`处理进度` 是回复生成前的思考状态，不是回复正文的尾注。`AgentRunMessage` 固定按“处理进度 → Markdown 正文 → 结构化内容 → 确认卡”的顺序渲染。

- 只有进度、尚无任何回复内容时，进度自动展开，实时展示已到达的业务阶段。
- 第一段非空正文、首个结构化内容块或审批确认任一出现时，视为回复已经开始，进度立即自动收起。
- 收起后仍保留在回复前，用户可以手动展开回看；不删除既有阶段，也不新增持久化状态字段。
- 历史消息依据自身已有的正文、结构化内容和审批信息直接呈现收起状态，刷新后不需要重放流事件。

## 错误与降级

- 可信 Tool 结果缺失或结构异常：确认卡显示“动作 N”，不展示 UUID，不阻断审批。
- “全身”与具体部位混用：作为明确参数错误返回，不猜测用户优先级。
- 候选查询无 eligible 动作：沿用成功的空候选结果与限制说明，不伪造动作。
- 审批或保存失败：沿用现有真实错误和终态，不返回假成功。

## 模块边界

- `agentbuilder/**` 只读取本次 Run 已有的 framework-neutral Tool 事件，不查询 Fitness repository 或 fitness schema。
- Fitness 的目标部位归一化留在 `fitness-service`；SQL 和动作事实仍由 `fitness-infrastructure` 管理。
- starter 只投影允许公开的审批字段，不承担动作查询。
- 前端只渲染服务端 proposal 和安全降级，不执行名称查询或任意 Tool。

## 测试策略

所有生产代码改动按 RED → GREEN 实施：

1. Runtime 测试先证明：候选/详情 Tool 返回名称后，审批事件的 proposal 包含对应名称，而审批记录的冻结参数仍只有 ID。
2. Runtime 测试覆盖名称缺失时使用“动作 N”，事件中不出现 UUID 作为展示名称。
3. Fitness service 测试覆盖单独“全身”归一为空部位偏好，并验证经验、器械、冲击限制仍进入原过滤器。
4. Fitness service 测试覆盖“全身”与具体部位混用仍被拒绝。
5. 前端 reducer/组件测试覆盖旧 `exerciseIds` proposal 的“动作 N”降级与可信名称渲染。
6. 前端 CSS 行为测试加载真实 `app.css`，验证对话正文、确认卡/建议词和辅助说明的最终字号。
7. 前端组件测试覆盖：只有进度时自动展开；首段正文到达后自动收起；进度 DOM 始终位于回复内容之前。
8. 运行相关 Vitest、TypeScript、ESLint、Java 定向测试、Spotless、编译与 `git diff --check`；涉及 agentbuilder 与 Fitness 两个模块时运行 architecture tests。

## 成功标准

- 新生成计划的确认卡只显示真实动作名称；可信名称缺失时显示“动作 N”，页面不再出现动作 UUID。
- `fitness_exercise_candidates_query` 接收单独的“全身”并返回全身均衡候选，不再报未知部位。
- AI 对话正文、确认卡、建议词和辅助说明达到已确认字号，390px 宽移动端无横向溢出。
- 处理进度在回复开始前展开并显示阶段流转；回复开始后自动收起，且始终位于回复内容之前。
- 审批冻结参数、确认幂等和训练计划保存结果不发生语义变化。
